# BENCHMARK_PLANv2.md — Evaluation Design

## Goal

The primary goal of this benchmark is to test whether TACM improves function-level bug localization from natural-language bug reports under a fixed context budget.

This benchmark is designed to answer three questions:

1. Does structural retrieval outperform naive retrieval on bug localization?
2. Which TACM components contribute measurable gains?
3. Where and why does retrieval fail?

End-to-end patch generation is a secondary downstream validation, not the primary proof.

---

## Evaluation Overview

The evaluation is split into two phases.

### Phase 1 — Retrieval Benchmark (Primary)

Input:
- Natural-language bug report text

Output:
- Ranked list of code functions
- Packed retrieval context under a fixed token budget

Goal:
- Rank the buggy function as high as possible
- Include the buggy function in the packed context as often as possible

Primary benchmark:
- BugsInPy function-level bug localization

### Phase 2 — Repair Benchmark (Secondary)

Input:
- Natural-language issue text
- Retrieved context from each system

Output:
- Candidate patch generated by the LLM

Goal:
- Solve the task end-to-end

Secondary benchmark:
- SWE-bench Lite

This phase is used to validate that retrieval gains translate into downstream repair, but it is not the main evidence for TACM.

---

## Phase 1: BugsInPy Retrieval Benchmark

### Dataset

Primary dataset:
- BugsInPy

Target size:
- 50 to 100 bugs in the first serious benchmark
- Expand later if results are stable

Sampling protocol:
- Stratified across projects
- Fixed random seed
- Maximum number of bugs per project
- Exclude bugs where the bug report is missing or too sparse
- Exclude bugs where the fix does not map cleanly to a function-level target
- Exclude pure test-only fixes
- Exclude dependency or environment-only failures with no meaningful code-localizable function target

The sampled task list must be frozen before comparing systems.

### Ground Truth Definition

Ground truth must be derived from the fix patch, not from TACM.

Definition:
- Ground truth is the enclosing production function containing the primary fix hunk
- If multiple production functions are substantially modified, record all of them
- If no enclosing function exists, mark the bug as out of scope for the function-level benchmark

Important:
- Do not use G1 or any TACM graph to define the benchmark label
- Static source analysis may be used to map patch hunks to enclosing functions
- Benchmark labeling must be independent of the retrieval method

### Query Construction

The query must be derived from the bug report, not from the fix commit.

Allowed query sources:
- Issue title
- Issue body
- Reproduction text
- Error description from the report

Leakage controls:
- Remove explicit function names
- Remove file names when they trivially reveal the target
- Remove stack traces if they directly reveal the buggy function
- Do not use commit messages, PR descriptions, or fix diffs in the query

Benchmark variants:
1. Title only
2. Title + body
3. Manually normalized NL query

The first benchmark should choose one variant and freeze it. My recommendation is:
- Title + body, lightly normalized for clarity, with all direct function-name leakage removed

### Retrieval Corpus

All systems must retrieve from the same corpus.

Default corpus:
- Production Python source files only

Exclude:
- Tests
- Documentation
- Examples
- Vendored code
- Generated files

This restriction should be identical for all methods.

### Token Budget

Use a fixed packed-context budget for the primary comparison.

Initial setting:
- 4000 tokens

Secondary setting:
- 800 tokens

Reason:
- 4000 is practical and large enough to expose packing behavior
- 800 is useful as a stress-test budget

Do not vary candidate-pool size across methods at a given budget.

---

## Systems Compared

The benchmark should compare a small set of systems first.

### Required Baselines

1. No retrieval
2. Naive RAG
3. BM25 only
4. G1 only
5. G1 + G2
6. G1 + G2 + G3
7. Full TACM

Notes:
- Naive RAG should be a standard chunk-based baseline
- BM25 only should operate over the same code corpus
- G1 only should isolate structural retrieval without semantic augmentation
- Full TACM should be the complete intended system

For the first paper-quality benchmark, do not include adaptive query weighting or an intent classifier unless that component is already stable and separately justified.

---

## Retrieval Protocol

For each task and each system:

1. Build or load the system index over the frozen corpus
2. Submit the same query text
3. Produce a ranked candidate list of functions
4. Pack the final context under the same token budget
5. Record both pre-packing and post-packing results

This distinction matters.

Candidate-stage evaluation measures:
- Whether the buggy function was ever retrieved

Packed-stage evaluation measures:
- Whether the buggy function survived selection under the token budget

This separation helps distinguish retrieval failures from packing failures.

---

## Metrics

### Primary Metrics

1. MRR
2. Recall@1
3. Recall@5
4. Recall@20
5. Packed-context recall
6. Average tokens used

MRR is the primary ranking metric.

### Secondary Metrics

1. Precision@5
2. Candidate-pool recall
3. Query latency
4. Index build time
5. Peak memory or index size

### Definitions

Candidate-pool recall:
- Whether the ground-truth function appears anywhere in the retrieved candidate set before budgeting

Packed-context recall:
- Whether the ground-truth function appears in the final context after budget-constrained packing

This split is required because TACM includes a resolver and budget allocator, not just a retriever.

---

## Statistical Testing

Report statistical uncertainty for all main retrieval metrics.

Recommended tests:
- Paired bootstrap over per-query reciprocal rank
- Paired permutation test for MRR differences
- Bootstrap confidence intervals for Recall@k

Minimum reporting standard:
- Mean metric
- 95% confidence interval
- Paired significance test against Naive RAG

Small deltas without uncertainty reporting should not be treated as strong evidence.

---

## Failure Analysis

Each miss should be labeled using a fixed taxonomy.

Failure categories:
1. Lexical gap
2. Candidate retrieval miss
3. Cross-file resolution failure
4. Wrong enclosing function
5. Budget truncation
6. Noisy graph expansion
7. Ranking error
8. Benchmark ambiguity

At minimum, report:
- Frequency of each failure category
- Representative examples
- Whether the failure is likely addressable by G2, G3, G4, or benchmark cleanup

This is important because TACM is a systems paper, not just a leaderboard paper.

## Phase 2: SWE-bench Lite Downstream Validation

### Dataset

Secondary dataset:
- SWE-bench Lite

Initial size:
- 50 tasks

The task subset must be frozen before evaluation.

### Purpose

This phase tests whether better retrieval leads to better repair outcomes.

It is not the primary evidence for TACM because repair performance depends on both retrieval quality and generation quality.

### Protocol

For each task:
1. Build the retrieval context using each system
2. Pass the packed context to the same LLM
3. Generate one patch
4. Evaluate using the benchmark harness

### Metrics

Primary metric:
- Pass@1 or percent resolved

Secondary metrics:
- Buggy function included in retrieved context
- Tokens used
- End-to-end latency

Important:
- If repair fails, record whether the buggy function was present in context
- This separates retrieval failure from generation failure

---

## Fixed Variables

These settings should be held constant across systems.

LLM:
- One fixed model for the main comparison

Generation settings:
- Temperature = 0
- Fixed max generation length

Retrieval budget:
- Same token budget for all systems within each run

Corpus:
- Same filtered production corpus for all methods

Task set:
- Same frozen task list for all methods

Prompt:
- Same answer format and instruction prompt for all methods

---

## Non-Goals

This benchmark is not designed to prove:
- universal superiority on all programming tasks
- optimal patch generation prompting
- model-specific prompt engineering tricks
- the value of every TACM feature simultaneously in one first pass

The benchmark is designed to isolate and measure retrieval quality first.

---

## Core Claim This Benchmark Supports

If the benchmark succeeds, the defensible claim is:

TACM improves function-level bug localization from natural-language bug reports under a fixed token budget, and these retrieval gains partially transfer to downstream repair.

That is a cleaner and more defensible claim than trying to prove the entire thesis in one benchmark.
